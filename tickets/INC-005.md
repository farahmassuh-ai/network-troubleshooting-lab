# INC-005: Headquarters can't reach the branch

| Field | Value |
|---|---|
| Area | Routing (Layer 3, OSPF) |
| Affected | All traffic between HQ and the branch; the branch's internet access |
| Fault time (SRV1) | 2026-11-04 01:04:14 PM |
| Status | Resolved |

## Reported issue

"Headquarters can't reach anything at the branch. Each site works internally."

## Impact

Every user at both sites lost cross-site connectivity: HQ couldn't reach any 10.2.x.x address and the branch couldn't reach HQ. The branch also lost internet access, because its default route is learned from HQ-R1 through OSPF. Traffic inside each site kept working, since each site's own subnets are directly connected to its gateway.

## Logs

SRV1:

```
01:04:14.564 PM  10.0.0.2 (BR-R1)  %OSPF-5-ADJCHG: Process 1, Nbr …
01:04:18.955 PM  10.0.0.2 (BR-R1)  %SYS-5-CONFIG_I: Configured from console by console
01:04:48.813 PM  10.1.0.1 (HQ-R1)  %OSPF-5-ADJCHG: Process 1, Nbr …
01:04:48.813 PM  10.1.0.1 (HQ-R1)  %OSPF-5-ADJCHG: Process 1, Nbr …
```

(Messages truncated on screen.) BR-R1 dropped the adjacency first, right when its configuration changed; HQ-R1 followed about 34 seconds later, consistent with its OSPF dead timer (40 seconds) expiring after the hellos stopped. BR-R1's messages still reached SRV1 because they were sent before its routes to HQ were withdrawn.

## Troubleshooting steps

| # | Command | Result | What it showed / ruled out |
|---|---|---|---|
| 1 | SRV1 SYSLOG | OSPF adjacency changes on BR-R1 (01:04:14) and HQ-R1 (01:04:48), plus a config change on BR-R1 | The routers stopped being OSPF neighbors; a config change on BR-R1 came first |
| 2 | HQ-R1: `show ip ospf neighbor` | Only 3.3.3.3 (HQ-CORE) FULL; 2.2.2.2 (BR-R1) missing | Baseline lists both. The WAN adjacency is gone, so HQ-R1 has no routes to the branch |
| 3 | BR-R1: `show running-config \| include passive` | Only `passive-interface default` | Baseline also has `no passive-interface GigabitEthernet0/0/0`. The WAN interface had become passive |

## Root cause

On BR-R1, the WAN interface Gi0/0/0 was made passive under `router ospf 1`. A passive interface stays up and keeps its address, but stops sending OSPF hellos. HQ-R1 stopped hearing BR-R1, its dead timer expired, and both routers removed every route learned from the other. The link itself was never down.

## Fix

On BR-R1:

```
configure terminal
router ospf 1
no passive-interface gigabitEthernet0/0/0
end
```

## Verification

- Smoke test, all as expected:
  - HQ-PC1 → 10.1.30.10: replies
  - BR-PC1 → 10.1.30.10: replies (crosses the WAN, so OSPF routes are back)
  - HQ-GUEST1 → 198.51.100.10: replies
  - HQ-GUEST1 → 10.1.30.10: blocked

## Prevention

- When a whole site is unreachable but the link is up, check `show ip ospf neighbor` first: a missing neighbor explains every missing route at once.
- With `passive-interface default`, the `no passive-interface` lines are what keep the network connected. Include them in config audits and compare with the baseline.
- Alert on `%OSPF-5-ADJCHG` messages that go to DOWN on WAN links: here they were the first sign, before any user called.
