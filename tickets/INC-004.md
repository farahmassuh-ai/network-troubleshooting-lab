# INC-004: HQ guest PCs show a 169.254.x.x address

| Field | Value |
|---|---|
| Area | Services (DHCP relay) |
| Affected | All Guest (VLAN 20) devices at HQ: HQ-GUEST1, HQ-GUEST2 |
| Status | Resolved |

## Reported issue

"Guest PCs at headquarters show a 169.254.x.x address."

## Impact

Any HQ guest requesting or renewing an address failed and fell back to APIPA (169.254.x.x), losing all connectivity, including the internet. Guests that still held an earlier lease kept working until it expired, so the outage would spread over time. HQ Staff and all branch users were unaffected, because their gateways' relay settings were untouched.

## Logs

Only a `%SYS-5-CONFIG_I` from HQ-CORE (10.1.99.1). No interface or protocol went down: the relay setting is silent when removed.

## Troubleshooting steps

| # | Command | Result | What it showed / ruled out |
|---|---|---|---|
| 1 | HQ-GUEST1: IP Configuration → DHCP | "DHCP failed. APIPA is being used", 169.254.118.11/16, no gateway | The DHCP request gets no answer; the PC self-assigned an APIPA address |
| 2 | Scope | Only HQ guests affected; HQ Staff and branch guests fine | DHCP server (HQ-R1) and its pools are working; the fault is specific to the HQ Guest VLAN's path to the server |
| 3 | HQ-CORE: `show running-config \| include helper` | One `ip helper-address 10.1.0.1` line | Baseline has two (Vlan10 and Vlan20). The relay on one HQ gateway is missing |

## Root cause

`ip helper-address 10.1.0.1` was removed from HQ-CORE's `interface Vlan20`. DHCP requests are broadcasts, and a Layer 3 interface doesn't forward broadcasts. Without the helper, HQ-CORE stopped relaying guest DHCP requests to HQ-R1, so they never reached the DHCP server.

## Fix

On HQ-CORE:

```
configure terminal
interface vlan 20
ip helper-address 10.1.0.1
end
```

## Verification

- HQ-GUEST1, IP Configuration → DHCP: "DHCP request successful", 10.1.20.11/24, gateway 10.1.20.1
- HQ-GUEST2: 10.1.20.19/24, gateway 10.1.20.1
- Smoke test, all as expected:
  - HQ-PC1 → 10.1.30.10: replies
  - BR-PC1 → 10.1.30.10: replies
  - HQ-GUEST1 → 198.51.100.10: replies
  - HQ-GUEST1 → 10.1.30.10: blocked

## Prevention

- A 169.254.x.x address always means "no DHCP answer": check the relay (`ip helper-address`) on the client's gateway first, then the DHCP server.
- Include `show running-config | include helper` on each gateway in routine audits and compare with the baseline; the removal produced no log message beyond a generic config change.
- Faults like this grow slowly as leases expire, so a single affected user may be the first sign of a VLAN-wide problem.
