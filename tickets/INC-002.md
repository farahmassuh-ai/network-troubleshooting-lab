# INC-002: HQ-GUEST2 gets no IP address

| Field | Value |
|---|---|
| Area | Switching (Layer 2, trunk) |
| Affected | HQ-GUEST2 (HQ-ACC2 Fa0/11, VLAN 20) and any other Guest device on HQ-ACC2 |
| Fault time (SRV1) | 2026-11-04 12:25:29 PM |
| Status | Resolved |

## Reported issue

"HQ-GUEST2 (Guest, on HQ-ACC2) gets no IP address. HQ-GUEST1 (Guest, on HQ-ACC1) is fine."

## Impact

Every Guest (VLAN 20) device on HQ-ACC2 lost all connectivity, because it couldn't get an address. HQ-GUEST2 was the only one connected. Staff, Servers and Management traffic on HQ-ACC2 kept working, and guests on HQ-ACC1 and at the branch were unaffected.

## Logs

SRV1, from 10.1.99.1 (HQ-CORE):

```
12:25:29.266 PM  %SYS-5-CONFIG_I: Configured from console by console
```

No interface went down, so the only trace was a configuration change on HQ-CORE.

## Troubleshooting steps

| # | Command | Result | What it showed / ruled out |
|---|---|---|---|
| 1 | HQ-GUEST2: `ipconfig /renew`, `ipconfig` | "DHCP request failed", 0.0.0.0 | Its DHCP request gets no answer |
| 2 | Compare with HQ-GUEST1 (works) | Same gateway, relay and DHCP server | Ruled out HQ-CORE Vlan20, the helper address, HQ-R1's DHCP pool and GUEST-IN. The fault is on the part of the path the two guests don't share: HQ-ACC2 and its trunk |
| 3 | SRV1 SYSLOG | Config change on HQ-CORE (10.1.99.1) at 12:25 | Something changed on HQ-CORE |
| 4 | HQ-ACC2: `show vlan brief` | Fa0/11 in VLAN 20 | Matches baseline; access port is fine |
| 5 | HQ-ACC2: `show interfaces trunk` | Gi0/1 allows 10,20,30,99 | Matches baseline; HQ-ACC2's end of the trunk is fine |
| 6 | HQ-CORE: `show interfaces trunk` | Gi1/0/3 allows **10,30,99**; Gi1/0/2 allows 10,20,30,99 | Baseline is 10,20,30,99 on both. VLAN 20 removed from the trunk to HQ-ACC2 only |

## Root cause

VLAN 20 was removed from the allowed-VLAN list on HQ-CORE Gi1/0/3, the trunk to HQ-ACC2. HQ-CORE dropped all Guest frames from HQ-ACC2, including DHCP requests. The two ends of the trunk disagreed: HQ-ACC2 still sent VLAN 20, but HQ-CORE wouldn't accept it. HQ-GUEST1 was unaffected because it uses the other trunk, Gi1/0/2.

## Fix

On HQ-CORE:

```
configure terminal
interface gi1/0/3
switchport trunk allowed vlan add 20
end
```

`add` appends VLAN 20 to the existing list. Without `add`, the command would replace the whole list and cut off VLANs 10, 30 and 99.

## Verification

- HQ-CORE `show interfaces trunk`: Gi1/0/3 allows and forwards 10,20,30,99 again (matches baseline)
- HQ-GUEST2 `ipconfig /renew`: 10.1.20.19/24, gateway 10.1.20.1 (correct Guest subnet; DHCP isn't required to hand back the same address as before)
- Smoke test, all as expected:
  - HQ-PC1 → 10.1.30.10: replies
  - BR-PC1 → 10.1.30.10: replies
  - HQ-GUEST2 → 198.51.100.10: replies
  - HQ-GUEST2 → 10.1.30.10: blocked

## Prevention

- Always use `switchport trunk allowed vlan add` or `remove` to change a trunk; the plain command replaces the list.
- After any trunk change, run `show interfaces trunk` on **both** ends and compare with the baseline.
- A `CONFIG_I` on a core switch with no matching change request should be reviewed. Here it was the only clue in the logs.
